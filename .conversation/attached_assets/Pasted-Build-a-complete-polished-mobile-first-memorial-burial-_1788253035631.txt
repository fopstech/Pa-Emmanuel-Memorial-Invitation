KEMI-6205

8. FORWARDING PROTECTION
========================

This is extremely important.

The invitation should be valid for ONE admission only.

Each invitation must have a status:

* pending
* confirmed
* checked_in
* disabled

When an invitation is first created:

status = pending

When the guest arrives, the usher checks the code.

If valid and not already checked in:

Show:

"VALID INVITATION"

Guest name

"Admission: 1 person"

Status:

"READY FOR ADMISSION"

Show a button:

"ADMIT GUEST"

When the usher clicks "ADMIT GUEST":

* Record the check-in time
* Change invitation status to checked_in
* Store the usher/admin who performed the check-in
* Prevent the invitation from being checked in again

After successful check-in show:

"ADMITTED"

"Guest: Adewale Abatan"

"Admission: 1 person"

"Checked in at: [time]"

"THIS INVITATION HAS ALREADY BEEN USED."

If someone tries to use the same invitation again, show:

"INVITATION ALREADY USED"

"This invitation has already been used for admission."

Do NOT allow another check-in.

==================================================
9. IMPORTANT SECURITY RULE
==========================

Do not trust the frontend.

All invitation validation and check-in operations must happen securely on the backend/database.

The frontend must NEVER simply decide that an invitation is valid.

Use server-side/database validation.

When checking in an invitation, use an atomic operation/transaction so that two phones trying to check in the same invitation at almost the same time cannot both successfully admit the same guest.

The check-in operation should only succeed if:

status != checked_in
AND
status != disabled

Then immediately mark it checked_in.

Record:

* invitation ID
* guest ID
* check-in timestamp
* admin/usher ID
